# Run в рамках задачи

Полностью прочитай файл для task-scoped Run с записью. Он дополняет
`agent-run.md` итогом всей задачи и отчётом. Комментарий, статус и чек-лист
основной навык направляет в отдельные references.

<a id="choose-the-handoff-outcome"></a>

## Выбери итог передачи

Каждый handoff задачи передаёт ровно один `taskOutcome` по готовности всей
задачи и semantic status kind, а не только последней просьбы или локализованного
имени/кода. Outcome – рекомендация; принятие Run не меняет статус:

- `work_completed`: вся задача готова. Рекомендуй первый допустимый переход
  в `review`, либо `done`, если review отсутствует.
- `review_passed`: только после успешной проверки в этом Run задачи, уже
  находящейся в semantic `review`; рекомендуй `done`.
- `direct_completion`: только при прямой просьбе пропустить проверку,
  разрешающем pinned rule либо если тот же авторизованный пользователь
  создал задачу и назначил её себе. Рекомендует `done`; даже тогда предпочитай
  `work_completed` без конкретной причины пропустить review.
- `no_status_change`: частичная/информационная работа, неуспешное review или
  незакрытые вопросы, блокирующие завершение. Безопасное значение, если
  прямая просьба может быть уже всей задачи.

Например, исполни `bridge.actions.finish` через
`continue_trelio_workspace_action` с точным открытым `workingDirectory`
и `summary`, `evidence`, `filePaths`, `nextAction`,
`taskOutcome=work_completed`.

`questions` и `no_status_change` нужны, только если ответ необходим для
выполнения, проверки или решения задачи. Не создавай блокирующий вопрос из
необязательного пустого срока, исполнителя, контроля или metadata.
При выполненных требованиях и transition policy выбирай готовый outcome,
сохраняя посторонние необязательные поля. Будущее обслуживание/улучшение может
быть следующим шагом, не превращаясь в незавершённую часть задачи.

## Отправь и подготовь предложения

После принятого task submit Trelio создаёт системный комментарий из
неизменяемого handoff и сохраняет рекомендацию статуса без изменения задачи.
Последовательные принятые Run одного пользователя группируются в пределах
календарного дня компании, детали каждого остаются доступны.

После принятия один раз вызови `get_task_review_context` с точной задачей/Run
и только нужными `proposalKinds`, включая `comment` для обязательного
сообщения человеку. Он возвращает свежие core/deadline, видимые controls,
полный checklist и выбранные proposal contexts. Используй общие верхнеуровневые
controls/checklists вместе с proposal state и переиспользуй снимки для
соответствующих процедур, без повторов `get_task`, sections и одиночных context
reads. Существенное промежуточное изменение/конфликт требует нового чтения.
Если backend выбрал local action, следуй ему, не подменяй mirror/remote plaintext.

Сообщение человеку готовь по `task-comment-proposals.md`. Заново оцени всю
задачу по итоговым доказательствам даже при записанном `no_status_change`:
это лишь рекомендация. Только готовая целиком задача получает отдельный
status proposal до необязательных вопросов. Частичная работа его не создаёт.

Примени `task-checklist-proposals.md` к свежему чек-листу. Частичная работа
может предложить точные выполненные пункты; неподтверждённые переходы не
создают карточку. До записи перечисли все карточки. Для двух и более –
`task-proposal-bundles.md` и один `render_task_proposals` с независимыми
решениями. Недостающие scope/permissions предложения не отменяют принятый результат.

Сообщи итог, проверки, материалы, вопросы и следующий шаг; укажи фактический
статус задачи и ожидающее решение. Принятый Run не меняет статус.
После успеха не проси отдельного принятия Workspace.
