# Предложения комментариев к задаче

Полностью прочитай файл по прямой просьбе предложить/подготовить комментарий
или ответ Trelio, а также для обязательного сообщения человеку после
содержательного принятого task Run.

<a id="route-the-request-independently"></a>

## Обработай просьбу отдельно

Явная просьба о proposal – отдельная native-операция Trelio с Run или без него,
включая поздний запрос при разработке исходников, после compaction или в ходе
другой операции. Сохрани её как ожидаемый результат и выполни до финального
ответа; текущий маршрут не превращает её в побочную подготовку текста.

При необходимости определи точную задачу по области/контексту. Не начинай
Run только ради proposal. Прямая задача использует `companySlug`, `projectSlug`,
`taskNumber`; принятый task Run – точный `runId`.

<a id="inventory-the-response-before-writing"></a>

## До записи определи весь ответ

До proposal write посчитай все нужные интерактивные карточки для каждой точной
задачи: comment, статус всей задачи, control-clear, checklist. При двух и более
прочитай `task-proposal-bundles.md` и используй один bundle. Не вызывай сначала
comment tool, чтобы лишь потом обнаружить необходимость другой карточки.

<a id="prepare-one-editable-draft"></a>

## Подготовь один редактируемый draft

Для единственной карточки без известного private proposal задачи следуй точному
`proposalProvider`: headless context, затем local render. Иначе один раз
вызови create-only `propose_task_comment`. Plain-задачи не содержат
`proposalProvider`: один вызов без provider preflight. `proposalText` уже
должен быть самостоятельным готовым к публикации общим итогом. Не пиши его
как дополнение, исправление, усиление или обновление прежнего неопубликованного
proposal либо автоматического handoff:

- Прямая задача: точный locator и краткий `proposalText` от первого лица;
  прямые proposals не принимают workspace `filePaths`.
- Каждый содержательный принятый task Run: принятый `runId`, краткий результат
  от первого лица и только полезные итоговые/промежуточные `filePaths`.
  Системный handoff – технический аудит и контекст агента; proposal –
  обычный комментарий людям. Не прикладывай все файлы Workspace.

Сервер проверяет authoring basis/state; на обычном пути одной карточки не
делай отдельные context/hash calls. Пропусти компактный инструмент и используй
`get_task_comment_proposal_context`, затем `render_task_comment_proposal`,
если в переписке уже есть proposal этой точной задачи, нужна тонкая корректировка
единственной карточки, сравнение с прежним публичным обсуждением или намеренное
упоминание участника с ещё неизвестным точным `@username`. Используй лишь
возвращённый username; не угадывай и не заменяй простым именем.

При `UNPUBLISHED_DRAFT_REQUIRES_CONTEXT` не повторяй `propose_task_comment`.
Прочитай контекст один раз и используй исключительно schema v4 `authoringBasis`:
`publicCommentsSnapshot.comments` содержит только опубликованные человеческие
комментарии; `pendingHumanUpdateBasis.acceptedRuns` – ещё не сообщённые
результаты Run от старых к новым; `currentDraft.bodyText` намеренно отсутствует.
Игнорируй drafts, видимые в переписке. Составь одну самостоятельную замену,
поздний Run заменяет конфликтующую раннюю работу. Не склеивай, не исправляй,
не отзывай и не пересказывай приватный текст. Если общий итог не добавляет
публично ничего нового, dismiss draft. Иначе render с точными revision и
`authoringBasis.snapshotSha256`.

Для нескольких карточек всегда читай `get_task_comment_proposal_context`
точной цели и передавай authoring-basis hash/revision с текстом в её
`commentProposal` одного `render_task_proposals`, включая обычный комментарий
принятого Run. Старый `render_task_comment_proposals` остаётся совместимостью
для comment-only клиентов, не основным bundle-маршрутом.

<a id="keep-publication-separate"></a>

## Публикация требует отдельного решения

Не публикуй автоматически. «Только предложи» означает draft в инструменте,
а не замену текстом ответа. Не обходи через `create_comment`. Даже в текстовом
клиенте вызови proposal tool и используй fallback; `publish_task_comment_proposal`
вызывай лишь после явного одобрения точного видимого текста и выбранных файлов.
После явного отказа публиковать вызови `dismiss_task_comment_proposal`.

Недостающее право блокирует только человеческий proposal, не принятие
постоянного результата Workspace. Обычные вложения задачи создаются лишь
при публикации оператором.

<a id="complete-before-reporting"></a>

## Заверши до отчёта

До финального ответа проверь каждую явную просьбу о proposal. Она выполнена
лишь после возврата редактируемого/rendered draft инструментом либо сообщения
о точной блокировке tool/OAuth/ACL/определения цели. Цитата, блок текста или
обещание предложить текст в финале не выполняют просьбу. При заблокированном
инструменте не подменяй proposal обычным текстом молча.
