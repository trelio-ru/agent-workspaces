# Trelio Agent Workspaces

Официальный плагин для работы Codex и Claude с управляемыми пространствами
Trelio уровня компании, проекта, досье и задачи, а также с актуальными навыками,
которые компания или отдельный проект включили для агентов.

Patch `1.6.2` добавляет сохраняемый человекочитаемый журнал Agent Run. Если
`WORKLOG.md` отсутствует, bridge materialize-ит стандартный шаблон; сохранённую
workspace-версию он никогда не подменяет. После чтения шаблона агент создаёт
для каждого содержательного Run отдельную запись в `worklog/`, поэтому Git
сохраняет происхождение результата без постоянного переписывания одного
растущего blob. Журнал содержит значимые действия, повлиявшие указания
оператора, основания решений, проверки и следующий шаг, но не внутреннюю
цепочку рассуждений, полную переписку, технический шум или секреты.
После публикации `1.6.2` backend patch поднимает общий hard minimum до этой
версии; миграции, новые env и OAuth scopes не требуются.

Patch `1.6.1` добавляет навык `trelio-project-access`. Он доступен только
владельцу и администраторам компании, управляет одной прямой ролью проекта за
операцию и всегда использует связку `plan_project_access_change` →
`apply_project_access_change`. Plan показывает сохраняющийся групповой,
company-wide и task-scoped доступ. Назначение и отзыв модератора требуют
отдельного подтверждения; точная прямая команда на участника, наблюдателя или
удаление – нет. Старому OAuth-подключению нужно повторно выдать новый scope
`mcp:project-access:manage`. После публикации плагина backend patch поднимает
общий hard minimum до `1.6.1`; Codex bridge использует штатный self-update.

## Установка

Добавьте GitHub-репозиторий как Codex marketplace:

```bash
codex plugin marketplace add trelio-ru/agent-workspaces
```

Команда отслеживает default branch официального репозитория. Такой marketplace
обновляется так:

```bash
codex plugin marketplace upgrade
```

Trelio проверяет версию bridge при preflight и во всех transport-запросах.
Версия ниже последнего опубликованного стабильного plugin release получает
`AGENT_WORKSPACE_PLUGIN_UPGRADE_REQUIRED` и не может открыть, продлить или
отправить Run. Начиная с `1.5.11`, Codex bridge тихо обновляет официальный
marketplace в фоне. При обязательном gate он сначала проверяет уже
установленную версию, при необходимости выполняет bounded update и безопасно
перезапускает exact новый bridge в той же задаче. Если текущий чат нельзя
перечитать, достаточно новой задачи; полностью перезапускать Codex нужно только
когда и новая задача остаётся на старой версии или не загружает MCP tools.
Существующую локальную папку можно продолжить повторным `open` того же Run.
Временный диагностический opt-out
`TRELIO_WORKSPACE_DISABLE_AUTO_UPDATE=1` отключает автоматический путь и
возвращает ручной update fallback, но не ослабляет server hard gate.

Начиная с `1.6.0`, change-prone платформенные правила приходят с
авторизованного backend Trelio. Compatibility preflight передаёт SHA-256
локального cache: при совпадении backend возвращает только metadata, при
изменении — exact immutable revision с Markdown. Bridge повторно считает
SHA-256, ограничивает размер, атомарно сохраняет проверенный cache и повторяет
preflight до отдельного ответа `current`, после чего передаёт hash в
start/claim. Exact revision затем входит в pinned
`context/agent-instructions.md`; активный Run не меняет правила посреди работы.
Универсальные security/transport invariants остаются в plugin bootstrap.

Источник, ранее добавленный с `--ref vX.Y.Z`, остаётся на выбранном tag. Чтобы
перевести его на обновляемый default branch, один раз выполните:

```bash
codex plugin marketplace remove trelio-plugins
codex plugin marketplace add trelio-ru/agent-workspaces
```

Затем откройте `Plugins`, выберите источник `Trelio` и завершите OAuth-доступ
в `Trelio Agent Workspaces`. Перезапуск клиента нужен только если новый
источник ещё не появился в `Plugins`. Marketplace устанавливает плагин
автоматически благодаря policy `INSTALLED_BY_DEFAULT`.
После OAuth начните новую задачу, чтобы сессия перечитала MCP-инструменты.
Полный restart нужен только если новая задача их не видит. При первом локальном
открытии workspace bridge
создаст одноразовую pairing-заявку, а агент сразу передаст её уже
авторизованному MCP и повторит исходную команду. Код пользователю не
показывается, писать подтверждение в чат не нужно. Если approval-policy
MCP-клиента требует подтверждать tool-вызов, клиент сам покажет одну штатную
кнопку; при автоматическом режиме останется только уведомление о подключении.
Bridge докажет владение локальным verifier и сохранит узкую device-session
только в приватном локальном файле – без зависимости от системной Связки
ключей. На macOS/Linux это
`~/.config/trelio/workspace-bridge/credentials.json` (`0700` для каталога,
`0600` для файла, owner/no-symlink checks и атомарная запись), на Windows –
`%LOCALAPPDATA%\Trelio\workspace-bridge\credentials.json` с ACL только для
текущего пользователя. Старое Keychain-значение device-session при наличии
один раз мягко переносится в файл. Если локальная запись после exchange не
прошла, bridge сам отзывает выданную server-session. Второй OAuth не
запускается, MCP token не копируется, а следующие Run используют ту же
device-session без дополнительных MCP-запросов. Права на рабочие правила, включая
`mcp:agent-instructions:manage`, остаются у основного MCP.

В первой новой задаче выберите starter prompt
`Настрой Trelio и доступные навыки для текущего проекта`. Onboarding проверит
компанию через MCP, безопасно добавит управляемый блок в корневой `AGENTS.md`,
подключит локальный компонент через `trelio-workspace login` без создания
тестовой работы агента и покажет актуальные навыки. Навыки с отсутствующей
общей конфигурацией получают статус
`требуется настройка администратором компании`; личные пароли, токены, коды и
сессии вводятся только в защищённых локальных формах.

В управляемой рабочей области администратор импортирует marketplace один раз и
назначает плагин нужным ролям. Каждый пользователь всё равно проходит OAuth
лично. Автоматическая установка не расширяет доступ вопреки policy рабочей
области.

Для разработки можно подключить текущий checkout публичного репозитория:

```bash
codex plugin marketplace add /absolute/path/to/agent-workspaces
```

Marketplace описан в `.agents/plugins/marketplace.json`; plugin manifest – в
`.codex-plugin/plugin.json`.

Для Claude Code / Claude Cowork добавьте тот же GitHub-репозиторий как
marketplace и установите `trelio-agent-workspaces`:

```text
/plugin marketplace add trelio-ru/agent-workspaces
/plugin install trelio-agent-workspaces@trelio-plugins
```

Claude manifest находится в `.claude-plugin/plugin.json`, а marketplace – в
корневом `.claude-plugin/marketplace.json`. После обновления marketplace клиент
получает новую версию плагина штатным механизмом Claude.

## Политика моделей и reasoning effort

Начиная с `1.5.5`, администратор компании может настроить в Trelio отдельное
правило для каждой известной модели Codex и Claude Code: запретить модель либо
разрешить её начиная с выбранного effort. Для новых неизвестных моделей
каждого провайдера и для других клиентов есть отдельные allow/deny правила.

Bridge перед `start`/`claim` читает реально наблюдаемые client/model/effort из
runtime Codex или Claude Code и передаёт их как `local_observed` attestation.
После materialization pinned policy сохраняется рядом с Run, а plugin hook
повторяет проверку перед каждым tool-вызовом. Поэтому смена модели или effort
посреди сессии не ослабляет уже закреплённое правило.

Режимы company policy:

- `disabled` – обратная совместимость без блокировки;
- `observe` – выполняет оценку, но не останавливает Run;
- `enforce` – не выдаёт lease и блокирует tool-вызов при запрещённой модели,
  недостаточном effort или отсутствии требуемых данных.

Claude Cowork пока не даёт плагину одинаково надёжные model+effort данные на
каждом действии. Поэтому он относится к «другим клиентам»: администратор
явно выбирает запрет или разрешение с более слабой гарантией. Та же развилка
работает для любых будущих клиентов.

`local_observed` не является криптографической аттестацией устройства:
локальный администратор технически может изменить установленный plugin или
отключить hooks. Контур предназначен для централизованного product guard и
защиты от случайной работы на запрещённой конфигурации, а не от владельца
скомпрометированной машины.

## Рабочие правила компании и проекта

В настройках Trelio администратор компании и руководитель проекта публикуют
Markdown-правила для агентов. Проектные правила дополняют корпоративные.
Каждая публикация создаёт неизменяемую версию с автором, временем и описанием
изменения; уже начатый Run никогда не переключается на новую версию.

Агент получает эффективный снимок при старте Run и читает его в
`context/agent-instructions.md`. Bridge при каждом `open` создаёт актуальный
защищённый `AGENTS.md`, который требует прочитать этот файл, но не хранится в
accepted Git и не попадает в candidate начиная с `1.3.12`. Правила компании и проекта не могут
расширить ACL, отключить backend-проверки, переопределить системные ограничения
Trelio или заменить прямое указание пользователя.

Через MCP агент может прочитать эффективные правила и подготовить точный diff
как по прямой просьбе пользователя, так и по собственной инициативе, если
обнаружил устойчивое правило для будущих Run. Он обязан показать полный diff,
причину и точную область изменения и может опубликовать новую версию только
отдельным вызовом после явного подтверждения пользователя. Для публикации нужен
scope `mcp:agent-instructions:manage`; старому OAuth-подключению требуется
повторный consent.

## Личные настройки агента

Каждый пользователь может сохранить отдельный company-scoped профиль «Как
агенту работать со мной». Профиль версионируется отдельно от правил компании и
проекта, закрепляется при старте Run и materialize-ится только в защищённый
read-only `context/user-profile.md`. Он не попадает в accepted Git, candidate
или workspace другого пользователя.

Перед изменением профиля агент обязан оценить правильную область: текущий
запрос, задача, пользователь, проект или компания. `plan_my_agent_profile_update`
создаёт personal diff только для personal scope. Project/company предложение
переходит в обычный rule flow после согласования, а task/current-request
требование не сохраняется как постоянный профиль. `publish_my_agent_profile`
требует exact personal plan и явное подтверждение пользователя; отдельный
admin scope не нужен, потому что tool может изменить только профиль
аутентифицированного участника и требует `mcp:workspaces:write`.

## Подключаемые навыки

Каталог Trelio может выдать актуальные навыки email, Telegram, MAX и 1С ЭДО. Обычные
параметры подключения хранятся в настройках компании, secret values — только в
Agent Secrets, а личные session/cookies и `policy.json` — локально:

```text
<trelio-config-home>/integrations/<skill>/<company>/<member>/<connection>/
```

Telegram `api_hash` не передаётся через MCP или чат: bridge получает его
одноразовым grant и передаёт только в environment точного executable. Telegram
`login` открывает защищённую одноразовую страницу на `127.0.0.1` в системном
браузере на macOS и Windows. На одной странице можно выбрать код Telegram или
автоматически обновляемый QR.
Если Telegram вернул подсказку 2FA, runtime показывает её только рядом с
локальным полем пароля после нормализации, ограничения длины и HTML-экранирования.
Все интерактивные формы и поля Telegram login явно отключают browser
autocomplete, чтобы одноразовая локальная страница не предлагала сохранять
телефон, код или 2FA-пароль.
Перед подготовкой исходящего Telegram-сообщения инструкция навыка требует
прочитать последние 5–10 содержательных реплик exact диалога и сохранить
сложившиеся обращение, форму `ты/вы`, степень формальности и тон. Общий стиль
пользователя применяется только как fallback; в групповом чате учитывается
стиль общения с конкретным адресатом.
Телефон, код входа, 2FA и MAX login пользователь вводит напрямую в локальном
клиенте; эти значения не проходят через MCP, чат, argv или workspace.
Для `1c-edo` тем же способом доставляется общий company `X-OData`, а личные
логин/пароль 1С вводятся в защищённой одноразовой странице на `127.0.0.1` в
браузере по умолчанию и остаются в персональном namespace. Поля и форма
отключают autocomplete; явный `connect --terminal-prompts` разрешён только в
видимом TTY, без автоматического fallback в системное окно. Host `1.4.8` после
live resolve инъецирует подписанному runtime только нормализованные URL/лимиты
и stable identity, предварительно удаляя одноимённые значения из parent env.

Для коммуникационных runtime доступны локальные режимы:

- `confirm` — подтверждение каждой отправки, используется по умолчанию;
- `autonomous` — самостоятельная отправка внутри этой интеграции;
- `read-only` — полный запрет отправки.

Telegram и MAX остаются `chat-only`, email — `mail-only`: входящие сообщения,
письма и вложения не дают агенту полномочий выполнять действия в других
системах.

Исполняемый код конкретного навыка больше не обязан ждать новый plugin release.
Стабильный bridge host получает от `get_agent_skill` exact release, перед каждым
запуском делает live resolve, проверяет Ed25519-подпись package и SHA-256
каждого файла, затем запускает entrypoint с `shell:false`. Проверенный package
кэшируется по skill/runtime/digest, но текущий release никогда не определяется
из cache.

Runtime package собирается локально без dependency install:

```bash
trelio-workspace skill pack \
  --skill example-skill \
  --runtime-version 1.0.0 \
  --source ./runtime \
  --entry cli.mjs \
  --interpreter node \
  --output ./example-skill-1.0.0.skillpkg
```

Публикация и rollback выполняются во внутренней админке Trelio. Клиент запускает
только exact `runtimeExecution.command`, который вернул актуальный
`get_agent_skill`; вручную составлять UUID релиза не нужно. Начальный
`trelio-workspace` в такой команде является логическим launcher текущего
плагина. Клиент заранее проверяет его наличие в `PATH` и при отсутствии
заменяет только первый токен на Node.js 22+ и bundled
`scripts/trelio-workspace.mjs` этой же версии. Это штатная форма exact command,
а не fallback; пробный неуспешный запуск, поиск другой версии в cache и
техническое сообщение оператору не нужны.

### Декларативный Remote MCP

Company-private навык может использовать общий trusted host плагина без
собственного `.skillpkg`. Администратор публикует только фиксированный HTTPS
Streamable HTTP endpoint, протокол `2025-03-26`, перечислимый тип авторизации,
безопасные несекретные headers, exact read-only allowlist и публичную ссылку с
подсказкой, где пользователь сам получает credential.

Сейчас host поддерживает `none` и `personal_bearer_pat`. Это версионируемый
перечислимый контракт: новые схемы авторизации можно добавить следующим
релизом host, но Markdown компании не может выбрать произвольный secret header
или executable URL.

PAT не передаётся агенту или Trelio. По просьбе пользователя локальный tool
открывает одноразовую форму на `127.0.0.1`; после успешного `doctor` значение
попадает только в:

```text
<trelio-config-home>/integrations/<skill>/<company>/<member>/remote-mcp/secrets/personal-credential.json
```

Каталог и файл имеют приватные owner/ACL/mode checks, не находятся в workspace
и не попадают в Git. Credential привязан к fingerprint endpoint, auth, headers
и allowlist: любое изменение декларации требует повторного локального ввода.
Удаление через local tool стирает только эту копию и не отзывает PAT у
провайдера.

Streamable HTTP обрабатывается как поток: host завершает конкретный JSON-RPC
запрос сразу после первого SSE event с exact matching `id`, даже если сервер
оставляет соединение открытым и продолжает heartbeat. Соединение после ответа
закрывается, а абсолютный deadline запроса не сбрасывается входящим трафиком.
Сам stdio host продолжает читать JSON-RPC во время ожидания формы или сети,
поэтому `notifications/cancelled` не застревает за активным `tools/call`.
Отмена протягивается до Trelio resolve, opener, loopback listener и Remote MCP
socket; закрытие stdin отменяет все активные вызовы и освобождает те же ресурсы.

Одноразовая форма считается открытой только после нулевого exit status
системного browser opener и фактического GET exact nonce URL. Если macOS
приняла `open`, но браузер не запросил форму, host приватно повторяет handoff
через Google Chrome и Safari. После всех неудач listener закрывается с
безопасной ошибкой; URL и nonce не возвращаются агенту и не предлагаются для
ручного копирования из чата.

Перед каждой фактической операцией host заново получает current release у
Trelio, разрешает DNS, блокирует private/reserved адреса, закрепляет проверенный
IP на соединение, выполняет `initialize` и требует точного совпадения
`tools/list` с опубликованным allowlist. Лишний, неизвестный, destructive или
write-like tool блокирует всё подключение. `Mcp-Mode: Write` и
`Mcp-Write-Spaces` host не отправляет.

Первый проверенный кейс – «База знаний Додо»:

- endpoint `https://knowledgebase.dodois.io/mcp`;
- токен пользователь получает по
  [`dodopizza.info/next/settings/mcp-tokens`](https://dodopizza.info/next/settings/mcp-tokens);
- allowlist: `current_user`, `get_announcements`, `get_content`,
  `get_space_content`, `get_spaces`, `preview_content`, `search_content`.

MAX использует версионированный browser adapter: accessibility-селекторы,
текстовые и геометрические fallback, дедупликацию результатов и проверку
результата отправки. Поиск может показывать частичные совпадения, но чтение и
отправка по названию разрешены только при одном точном нормализованном
совпадении; иначе нужно использовать официальный URL чата. Команда `probe`
ждёт интерактивную поверхность SPA, при пустом первом shell один раз безопасно
перезагружает страницу и возвращает только UI-fingerprint без текстов чатов,
сообщений, cookies и credentials. Если интерфейс нельзя распознать однозначно,
runtime закрывается с ошибкой и не отправляет сообщение.

## Поиск задач и связанный контекст

До выбора writable workspace агент сначала ищет существующую задачу в области,
разрешённой локальным `AGENTS.md` или запросом пользователя. Поиск Trelio
обычный, не семантический: агент формирует 5–12 коротких синонимов, сокращений и
вариантов названия и передаёт их отдельными элементами одного вызова
`search_tasks`. Backend ищет каждый вариант независимо, повторно проверяет MCP
policy и task ACL, дедуплицирует задачи и ставит выше совпавшие с несколькими
вариантами. Склеивать все слова в одну длинную строку нельзя.

Найденный кандидат проверяется через `get_task`; похожего названия без второго
независимого признака недостаточно. После подтверждения агент использует task
workspace. Если предмету нужен долговременный контекст, но он не принадлежит
одной задаче, агент сначала ищет или создаёт отдельное Git-backed досье.
По умолчанию досье принадлежит проекту; company-досье допустимо только для
действительно межпроектного контекста, безопасного для всех участников
компании, и требует явного подтверждения широкого доступа.

Досье остаётся агентским субъектом без отдельной web-страницы и публичной
ссылки. Оно может быть связано с несколькими задачами. Участник связанной
задачи с полным доступом к ней получает read-only доступ к досье и его принятым
файлам, но не получает доступ к проекту-владельцу, запись в досье, Agent Run
или управление связями. Связать или отвязать досье может только пользователь,
у которого независимо есть права на само досье и редактирование задачи.

Project workspace предназначен для общих материалов проекта, а company
workspace – только для материалов всей компании.

Агент может сам искать принятые text-файлы во всех workspace, которые доступны
пользователю, и читать точный найденный head. Для известной связанной задачи,
проекта, досье или компании он может получить workspace напрямую по scope.
Обычные ACL перепроверяются на каждом результате; связь между задачами не
открывает доступ к закрытой задаче или её файлам.

Выбранный workspace прикрепляется к активному Run как pinned read-only
`related` context. Bridge материализует его рядом с parent context:

```text
context/index.json
context/agent-instructions.md
context/user-profile.md
context/company/
context/project/
context/related/<workspace-uuid>/
```

Если агент прикрепил контекст после локального `open`, достаточно выполнить:

```bash
trelio-workspace context attach --workspace <uuid>
trelio-workspace context sync
```

Первая команда использует актуальные lease/fencing из локального Run,
прикрепляет workspace и сразу синхронизирует его. `context sync` отдельно
обновляет уже прикреплённые через MCP revision. Bridge скачивает Git bundle,
обычные inline text-файлы и точные object pointers, но не external object bytes,
и атомарно заменяет локальные read-only snapshots. Единственный каталог
`workspace/` остаётся writable и только он попадает в candidate.

Конкретный бинарный или крупный файл read-only context материализуется лениво:

```bash
trelio-workspace context fetch --path ../context/project/sources/manual.pdf
```

Skill распознаёт пятистрочный workspace-object pointer и вызывает эту команду
перед чтением выбранного файла. Полной фоновой догрузки нет. Backend
авторизует exact `runId`, dependency workspace, pinned head и path, затем bridge
проверяет размер и SHA-256. Проверенные bytes публикуются атомарно в локальный
content-addressed cache вне Run и повторно используются следующими Run.
Snapshot создаётся через clonefile/reflink с fallback на независимую копию;
mutable hardlink не используется. Writable `workspace/` пока материализуется
eager, чтобы сохранить совместимость candidate/submit.

## Ожидание решения и продолжение на другом компьютере

Перед вопросом, без ответа на который работа не может продолжаться, агент
создаёт blocker через локальный bridge:

```bash
trelio-workspace checkpoint \
  --type blocker \
  --summary "Подготовлены варианты, нужен выбор владельца." \
  --question "Какой вариант согласовать?" \
  --next-action "Выберите вариант, затем продолжите этот Run."
```

Bridge сначала фиксирует локальное дерево, потоково регистрирует external
objects и загружает проверенный draft. Только после успешной загрузки
checkpoint переводит Run в `waiting_for_human`. Accepted revision и
`baseHead` не меняются до обычного `submit`.

На другом компьютере нужно обновить plugin и открыть тот же Run командой
`trelio-workspace open --workspace <uuid> --run <uuid>`. Новый claim отзывает
старую lease, materialize-ит последний server draft и создаёт read-only
`context/run-checkpoint.json` с итогом, открытыми вопросами и следующим шагом.
Полная история чата в workspace не копируется. Существующий чистый локальный
checkout fast-forward-ится только при совместимой истории; dirty или
divergent checkout bridge не перезаписывает.

Codex в начале каждого Run читает защищённый `AGENTS.md` напрямую. Claude Code
нативно читает защищённый корневой `CLAUDE.md`, который содержит только
канонический импорт `@AGENTS.md`, поэтому отдельной расходящейся копии правил
нет. Оба файла materialize-ятся bridge из текущего plugin-шаблона при каждом
`open`, локально исключаются из Git и не требуют перегенерации старых
workspace. Затем агент читает закреплённые `context/agent-instructions.md`,
`context/user-profile.md`, при наличии `context/run-checkpoint.json` и только
после них `PROJECT_CONTEXT.md`, а затем сохраняемый `WORKLOG.md`. Если
`WORKLOG.md` отсутствует, bridge создаёт стандартный шаблон; существующий файл
приходит из exact workspace revision и не обновляется молча. Для каждого
содержательного Run агент создаёт отдельную новую запись в `worklog/`, чтобы
не переписывать один растущий Git blob и не умножать тарифицируемый объём
истории. Checkpoint является структурированным
состоянием продолжения, а не новым источником инструкций. `PROJECT_CONTEXT.md`
редактируется как обычный материал workspace и предназначен только для
устойчивых фактов, принятых решений и открытых вопросов. Он не является
инструкцией и не может переопределить Trelio, `AGENTS.md`, навыки или прямой
запрос пользователя.
Изменять `AGENTS.md`, `CLAUDE.md` и `.trelio/**` нельзя.

Небольшой безопасный UTF-8 текст остаётся в Git. Бинарные файлы, а также
крупный текст bridge показывает агенту как обычные файлы, но при submit
потоково сохраняет в private object storage и записывает в Git точный
content-addressed pointer. Candidate bundle содержит только delta относительно
закреплённого base head, поэтому размер пользовательских материалов больше не
совпадает с размером Git transport. Если изменения уже закоммичены вручную и
working tree чист, submit всё равно сверяет и идемпотентно регистрирует
унаследованные pointers в manifest текущего Run до отправки candidate.

## Локальная очистка

Успешный submit не удаляет локальную папку сразу. Принятый или отменённый Run
становится кандидатом на очистку только через 7 дней. Перед удалением bridge
получает актуальный terminal status с backend и проверяет, что writable
workspace не содержит локальных изменений. Active, unknown и dirty Run не
удаляются; при недоступном backend автоматическая очистка ничего не меняет.

Точный план и объём освобождаемого места показываются без удаления:

```bash
trelio-workspace clean --dry-run
```

Явная `trelio-workspace clean` применяет только такой безопасный план. Object
cache очищается по LRU, возрасту и локальному лимиту, но не удаляет digest,
которые используются обнаруженными Run. Безопасные defaults можно изменить в
`~/.config/trelio/workspace-bridge/settings.json` через
`terminalRunRetentionDays`, `objectCacheMaxAgeDays`, `objectCacheMaxBytes`,
`skillRuntimeCacheMaxAgeDays` и `skillRuntimeCacheMaxBytes`.

Простые связи задач не требуют общего кейса. Агент описывает смысл прямой
связи свободной подписью, а направленность задаёт отдельно. Рабочий кейс
используется только для одного предмета, представленного несколькими задачами.

## Живой каталог навыков

Начиная с plugin `1.5.0`, skill-first routing больше не зависит от того,
активировал ли агент bootstrap-навык. Постоянно подключённый bundled MCP host
`trelio-remote-skills` возвращает обязательный gate через стандартное
`initialize.instructions` до выбора конкретного инструмента. Для company или
project context агент сначала вызывает `list_agent_skills`, выбирает навык по
назначению и непосредственно перед действием читает его через
`get_agent_skill`.

Если каталог вернул `runtimeExecution`, допустим только его exact command; для
`remoteMcpExecution` допустим только локальный trusted host с exact
identity/release. Нельзя подменять найденный навык браузером, Computer Use,
прямым HTTP, другим MCP или локальным скриптом. Отсутствие отдельного tool в
текущем списке не означает отсутствие интеграции. Fallback разрешён только при
реальном отсутствии подходящего назначения, ненастроенном навыке/обязательном
подключении или неподдерживаемой операции, и агент обязан назвать эту причину.
Недоступный control plane `list_agent_skills` / `get_agent_skill` является
отдельной ошибкой, а не доказательством отсутствия интеграции.

Для exact command начальный `trelio-workspace` является логическим launcher
текущего установленного плагина. Агент разрешает его до выполнения и, если
PATH-entry отсутствует, сразу запускает bundled bridge этой же версии через
Node.js 22+, сохраняя остальные аргументы буквально. Такое разрешение не
является fallback или обходом skill-first gate и не требует сообщения
оператору, пока один из двух штатных launcher-вариантов доступен.

Штатные операции Trelio MCP и Agent Workspace через MCP tools и bundled bridge
`trelio-workspace` являются основным workspace workflow, а не fallback из
каталога Agent Skills. Обязательная проверка каталога для resolved context
сохраняется, но агент не ищет и не объявляет отсутствие отдельного навыка для
поиска задач, управления workspace/Run, чтения workspace context, checkpoint,
submit или restore. Явная причина fallback нужна только при выборе другой
реализации операции, которую мог бы выполнить релевантный catalog skill.

Bootstrap-навык `trelio-skill-catalog` получает через Trelio MCP текущий список
навыков компании и конкретного проекта. Корпоративные и проектные назначения
складываются; отключение назначения не удаляет и не запрещает личный навык
пользователя. Инструкции загружаются непосредственно перед применением и не
фиксируются в Agent Run, поэтому новая опубликованная версия доступна при
следующем чтении каталога.

`trelio-workspace-worker` обязательно получает этот живой каталог один раз
после определения точной компании и проекта. Для выбора достаточно безопасных
описаний из `list_agent_skills`; полный Markdown каждого навыка заранее не
загружается. `get_agent_skill` вызывается только для релевантного навыка и
непосредственно перед его фактическим применением. Если ответ содержит
`runtimeExecution`, агент выполняет его exact command. Host заново разрешает
release при каждом запуске, поэтому новая версия подхватывается без обновления
плагина; гонка между чтением инструкции и запуском возвращает
`AGENT_SKILL_RELEASE_CHANGED` и требует повторного `get_agent_skill`.

Первый навык – электронная почта через обычные IMAP/SMTP. Плагин включает
dependency-free CLI `scripts/trelio-email.py` для Python 3.11+: поиск, чтение,
список и сохранение выбранных вложений, диагностику и подтверждаемую отправку.
Gmail API не нужен. Для Gmail, Mail.ru, Яндекса и некоторых корпоративных
серверов может понадобиться пароль приложения и отдельное разрешение IMAP/SMTP.
Для Gmail CLI сразу показывает официальную прямую ссылку
[`https://myaccount.google.com/apppasswords`](https://myaccount.google.com/apppasswords),
подставляет `imap.gmail.com` / `smtp.gmail.com` и удаляет пробелы из показанного
Google 16-символьного пароля до его сохранения.

Первичная настройка выполняется интерактивно, чтобы пароль не попадал в shell
history:

```bash
python3 scripts/trelio-email.py configure --account work
python3 scripts/trelio-email.py doctor --account work
```

По умолчанию пароль вводится не в терминале: на macOS открывается системный
hidden-answer dialog, на Windows – модальное системное окно с masked-полем.
Если GUI недоступен в headless-среде, CLI сообщает об этом и использует скрытый
terminal fallback. Режим можно явно выбрать через
`--password-input window|terminal|auto`.

На macOS пароль сохраняется в Keychain. На других системах используется файл
`~/.config/trelio/email/secrets/<account>.password` с закрытыми правами; его
можно заменить переменной окружения `TRELIO_EMAIL_PASSWORD_<ACCOUNT>`.

## Agent Secrets

Trelio хранит значения Agent Secrets зашифрованно и выдаёт локальному bridge
только одноразовые grants конкретного Agent Run. Сам Trelio не запускает
внешние команды. Значение не возвращается в MCP и не попадает в workspace.

После `prepare_agent_secret_checkout` bridge запускается так:

```bash
trelio-workspace secret exec --grant <uuid> -- <executable> [args...]
```

Начиная с `1.5.6`, grant для логического executable `trelio-workspace`
запускает текущий проверенный bridge через его собственный Node.js process, а
не ищет одноимённую программу в `PATH`. Поэтому установленному Codex/Claude
plugin не нужен глобальный wrapper, а подмена `PATH` после выдачи grant не
может перенаправить company secret в другой executable.

Агент может записать значение, которое уже выдаёт локальная программа или
защищённый файл, напрямую в vault без MCP tool argument:

```bash
producer-command | trelio-workspace secret set --secret <uuid>
trelio-workspace secret set --secret <uuid> --file /secure/local/path
```

Команда работает только внутри активного materialized Run. Не передавайте
literal value параметром командной строки и не создавайте ради него файл в
workspace.

Для `file` delivery путь доступен локальной программе в
`TRELIO_SECRET_FILE`; временный файл имеет права `0600` и удаляется после
завершения процесса. Новые MCP OAuth scopes выдаются повторным подключением
плагина в Codex/Claude; локальный `trelio-workspace login` не расширяет права
MCP.

## Что видит оператор

Для task-scoped работы агент предлагает смысловые изменения как один
редактируемый комментарий через `get_task_comment_proposal_context` и
`render_task_comment_proposal`, но не публикует его сам и не останавливает из-за
него Run. Codex и Claude Cowork показывают стандартный MCP App с полем и кнопкой
«Опубликовать»; text-only клиенты получают предложение в fallback и вызывают
`publish_task_comment_proposal` только после явной команды человека. Пока
предложение не опубликовано, следующий вариант заменяет его свежей краткой
сутью изменений после последнего опубликованного комментария, а не склеивает
старые тексты. Перед записью агент сохраняет handoff с итогом, подтверждениями,
подготовленными материалами, открытыми вопросами и следующим действием.

После проверок Trelio принимает revision автоматически, только если pinned
`baseHead` всё ещё актуален. Успешная task-scoped приёмка создаёт системный
комментарий из handoff; последовательные Run одного пользователя в пределах
календарного дня компании группируются с раскрываемыми итогами каждого запуска,
как и остальные системные комментарии. Manual comment не является условием
handoff или submit. При конфликте агент начинает новый Run от текущей версии и
переносит изменения осознанно. UUID, полный Git SHA, lease/fencing и
bridge-команды остаются диагностическими деталями и не подменяют рабочий отчёт.
